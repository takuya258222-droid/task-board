# タスクボード

ユーザーの未対応タスクをタブ別に整理して表示し、画面上の「完了」が既存のタスク管理システム全体に反映されるWebページ。既存の家事アプリ・西STリストと同じ方式（Googleシート + Apps Script API + GitHub Pages）。

## 構成
- フロント: `github-page/`（index.html 単一ファイル + PWA: manifest.json / service-worker.js / icon.svg）。GitHub Pages で公開（予定URL: https://takuya258222-droid.github.io/task-board/ ）
- API: `apps-script/Code.gs`。シートの読み取り（state）と、ボード操作の「処理待ち」への記録だけを行う。実処理は同期ジョブ側。
- データ: Googleシート「タスクボード」 ID `1NNK6qcSQpwgZPwuceHRvBJeTTy6IekZX2OWNfZjXKj0`
  https://docs.google.com/spreadsheets/d/1NNK6qcSQpwgZPwuceHRvBJeTTy6IekZX2OWNfZjXKj0/edit
- 同期: cron `task-board-sync-0845 / -1200 / -1500 / -1730 / -1930`（平日5回、祝日ガード、owner goal:goal、配信先=タスク通知チャット）。5本とも本文は同一（検証済み）。v2で軽量化: 変化検知（状態ファイルのハッシュ＋未適用件数＋スナップショット比較）により、変化のない回は「軽量ラン」として再構築せずに終了する。08:45の回だけは必ずフル再構築。フル時もタブ単位の差分書き込み。

## 仕組み（重要）
- ボードの「完了」は、同期ジョブが元のSlackメッセージに ✅ を付けることで反映される。既存の各チェック（メール/Slack/カレンダー/面談/入社/フォローアップ）が次回実行時に通常の✅完了として検知するため、リマインド停止・リスト除外・面談パイプラインの前進まで既存機構で全部つながる。
- 既存のSlack共有（#面談-見学・自分宛DMの送信/リマインド）は無変更。ボードURLはSlackに貼らない（例外: 自分宛DMのリスト系5ジョブ末尾への1行追加と、完成時の納品DM1回のみ。いずれも親側で実施）。
- 同期ジョブが読み書きする状態ファイル: `~/workspace/goals/goal/hidden_files/` の5チェックファイル + members.md + board-assignments.md（割当専用、このジョブだけが触る）+ board-sync-snapshot.md（軽量化用スナップショット、このジョブだけが触る）。

## シートのタブ
- タスク（A:U）: 表示データ。同期が全量差し替え。id は `<type>:<元メッセージts>`、割当タスクのみ `assign:<割当ID>`。
- 処理待ち（A:L）: ボード操作のキュー。action の表記は complete / add / caseLost / caseClose / addMember / memberOff / reopen / delete。status は 未適用/適用済/失敗/対象外。失敗行は再試行されない（ボード上に「反映失敗」が出て、ユーザーが再操作できる）。J/K列は add=タイトル/日時、addMember=名前/メール、addMeeting=テキスト/担当、addStart=テキスト/入社日。L列は add・addStart の担当者。M列は addStart の書類回収済みフラグ（"1" のみ、それ以外は空）。reopen 行の B は完了履歴の id、delete 行の B はタスクの id（いずれも H/I に元メッセージの channel/ts）。
- 案件（A:I）: 進行中の面談案件。stagesJson に段階ごとの状態。
- 完了履歴（A:J）: 直近の完了・終了（最大60件）。A:F は従来どおり。G=id（taskId形式。割当は assign:<割当ID>、案件終了は case:<イベントID>）、H=reopenable（戻せる行だけ "1"）、I=channel、J=ts（元メッセージ。案件終了行は空）。
- メンバー（A:F）: members.md の写し（無効含む）。

## 機能
- タブ: すべて/メール/Slack/カレンダー/面談/入社/メンバー/完了済み。件数バッジ、期限超過は赤、今日が期限は強調、フェーズ色（面談カード左帯）。
- 検索、絞り込みチップ（担当/フェーズ/期限超過のみ）、既定ソートは既存優先順位（超過→締切近い順→古い順）。
- サマリー: 未対応総数/期限超過/反映待ち、次の面談。
- 面談タブ: 案件グルーピング。案件タップで詳細（①→⑤進捗、段階状態、Slackリンク）。案件アクション「失注にする」「案件を終了」は tour-prep-check.md への終了記録のみ（Slackメッセージは消さない。準備段階の終了=離脱、内定確認の終了=クローズとして記録）。
- タスク追加: 担当者セレクト付き。自分宛=カレンダー【タスク】登録（ひとことメモ方式）。メンバー宛=同期が次回にそのメンバーへDM送信し、board-assignments.md で管理（✅回収、24時間超で1日1回までスレッドリマインド、締切当日の朝も。ボードから「完了」で閉じることも可）。
- メンバー管理: 追加フォーム（名前+メール→members.md登録、Slack ID解決とカレンダー確認を試行、不足は通知チャットへ報告）/ 既存メンバーの無効化トグル。いずれも次回同期から反映。
- 人ごとの残タスクまとめ（v2追加）: メンバータブに、自分＋有効メンバーごとの「まとめをコピー」ボタン。その人の未対応分（担当の面談ステージタスク・メンション共有・依頼共有・割当タスク）を期限つきテキスト（見出し「【名前さん】未対応 ○件（M/D時点）」、期限超過は「⚠️期限超過」付き、並びは優先順位どおり、メンバー向けは末尾に✅依頼の1行）にまとめ、クリップボードへコピー（失敗時はテキストエリア表示にフォールバック）。ユーザーがコピペで送る用途で、自動送信はしない。0件の人にはボタンを出さず「未対応なし」と表示。
- 反映待ちの行には次回同期の目安（平日 8:45/12:00/15:00/17:30/19:30）を表示。
- 戻す（v2）: 完了済みタブで、✅完了したメール/Slack/カレンダー/メンバー共有/割当タスクと、次フェーズ未送信の面談段階タスクに「未対応に戻す」ボタン。同期が元のメッセージの✅を取り消し、状態記録を未対応に戻す（各チェックが次回に通常の未対応として再検出）。面談で次フェーズ送信済み・案件終了済みの場合は適用が「失敗」になり、理由がボードに出る。入社の完了と案件の終了（失注・離脱・クローズ・終了）は戻せない。割当の「対応済み（✅検知）」はメンバー本人の✅を消せないため、戻すと「✅リセット待ち」になり、メンバーが✅を外して付け直すと回収される。
- 物理削除（v2）: 未対応タスクの各行に「削除」ボタン（「完了」とは別物。2段階確認で、種別ごとの結果を明記）。同期の適用は既存の削除セマンティクスどおり: メール/Slack=利用者削除として記録上クローズ（メッセージ・下書きは消えない）、カレンダー【タスク】=カレンダー予定自体を削除、面談=段階ごとの削除ルール（①準備=離脱、②内定確認=クローズ、③書類回収・④入力・申請・⑤入職フォロー=削除は完了と同じ扱い）、入社=そのステージのみクローズ、メンバー共有=ユーザー確認済みとしてクローズ、割当=取消（DMは残る）。削除した項目は完了履歴に「削除」（面談③④⑤は「削除（完了扱い）」）として残る。
- PWA: ホーム画面に追加可能（アプリ名「タスクボード」）。

4. 完成時に自分宛DM（D0BGG9SUBEK）へ納品メッセージを1回送る。

## 運用メモ
- 同期1回の所要は状態ファイルの読み込み量次第で約10分（初回実測）。5回/日を超えて増やさないこと（無料枠配慮）。v2の軽量化で、変化のない回は軽量ランとして短時間で終了する（フル再構築は08:45必須＋変化があった回のみ）。
- 処理待ちの古い行は監査ログとして残る。テスト行 atest-* は掃除済み（ダミー行は空に）。
- ✅を押し間違えたら、元のSlackメッセージの✅を外せば既存チェック側で未完了に戻る（ボード表示も次回同期で戻る）。

## v17 追記（2026-11-18・フロントのみ）
- **「内定まで一括で進める」ボタン**: ユーザー要望「準備①②から内定まで一括でアプリ側でガンガンステータス進められるようにして」への対応。案件ごとに段階タスクを1つずつ完了しなくても、ワンタップで準備段階を全部完了して内定まで進められるようにした。「内定にする」の上位互換として併置する。
- **表示条件**（`canBulk`）: 未確定（内定前）で現在フェーズが①準備または②内定確認の案件で、内定までの道筋があるものだけ。道筋 = ②未送信で offer の先行確定ができる（`canOffer`）、または実在する②内定確認タスクを完了できる。①タスクしか無い案件（内定まで届かない）・②タスクが反映待ちの案件・内定確定済み・案件アクション反映中・先行確定の反映待ちの案件には出さない。③以降の段階は回収チェックリストの役割なので、このボタンでは進めない。
- **設置場所**: (a) 案件詳細ビューの offer ゾーン（「内定にする」と同じゾーンに併置）、(b) 面談タブの案件グループヘッダー直下（`.group-acts`、「内定にする」と同じエリア）。いずれも同じ `bulkDecide` ハンドラを使う。紫色の専用スタイル（`.bulk-btn`）で「内定にする」（緑）と区別する。
- **動作**（`bulkDecide` / `bulkTargets` / `bulkCompleteOne`）: その案件の①準備・②内定確認の段階タスクのうち、未完了で実在する（open な）ものを段階順（①→②、同一フェーズ内はタスク並び順）に全て complete POST する。各タスクの楽観完了は通常の「完了」と同じ表示処理（`optTasks` 記録・カード除去・履歴行追加）だが、`optDecided` には触らない。②内定確認タスクが実在した場合は、その完了が内定確定になるため offer は送らず、全 POST の成功後に初めて `optDecided`（`applyCaseDecided`）を適用して入社待ちへ即移動させる。②タスクが未送信の場合は、最後に offer の pending POST（`decideOffer` を流用。成功メッセージは一括側でまとめて出すため `opts.quietOk` を追加し、戻り値を boolean 化した）で内定にする。対象タスクが無く offer のみの場合は実質「内定にする」と同じになる。
- **途中失敗時**: その時点で中断し、理由を表示する（optFail で失敗したタスクだけ巻き戻し、完了済みがある場合は「○件のタスクは完了として記録しましたが、内定までは進めていません」と経過も表示）。既に成功した完了は正規の操作としてそのまま残し、巻き戻さない。内定確定ステップまで成功していない場合は `optDecided` を適用しないので、案件は面談待ちに残る。
- **二重タップ防止**: 実行中は `bulkRunning` で再入を防ぎ、全ての当該ボタンを無効化して「進めています…」表示にする。
